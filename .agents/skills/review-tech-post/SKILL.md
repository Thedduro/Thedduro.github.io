# 기술 블로그 검수

검수는 문제 목록을 만드는 데서 끝나지 않는다. 요청받은 글에서 필요한 부분을 수정하고, 기술적으로 정확하면서도 개발자가 이해한 내용을 자연스럽게 풀어낸 글로 마무리한다.

## 범위와 입력

- 대상 글 또는 메모리상의 초안, 사용자 수정 요구, 기존 조사 결과와 검증 범위를 확인한다.
- [write-tech-post](../write-tech-post/SKILL.md)의 문체 참고 방법·글쓰기 규칙·게시물 형식을 읽는다. 이를 기준으로 검수하되 새 글 생성 흐름을 다시 시작하지 않는다.
- 지정된 기존 글의 검수·수정 요청은 필요한 부분의 수정을 포함한다. 사용자가 읽기 전용 검토나 문제 목록만 요청했다면 수정하지 않는다.
- 관련 없는 게시물·설정·코드는 수정하지 않는다. 기존 글에서는 요청 범위와 관계없는 전면 재작성, 제목·URL·날짜·분류·공개 상태 변경을 피한다.

## Technical Review

문체의 자연스러움과 별개로 다음을 검수한다.

- 개념·실행 순서·기본값·전제·제약에 기술적 오류가 있는가.
- 대상 API와 언어·실행 환경이 정확한가. 비슷한 이름의 API를 혼동하지 않았는가.
- 설명, 출처, 예제가 같은 버전을 다루는가. 버전 차이를 보편적 동작처럼 서술하지 않았는가.
- 코드에 잘못된 API 호출, 빠진 import·입력·의존성, 잘못된 예상 결과가 있는가.
- 실행 가능한 예제와 발췌·의사 코드가 구분되는가. 실행하지 않았는데 테스트했다고 주장하지 않는가.
- 성능 수치·사용자 경험·인과관계에 근거가 있는가. 성립 조건을 생략해 “항상”, “무조건”이라고 단정하지 않는가.

사실이나 API 동작을 다시 확인해야 하면 [research-tech-topic](../research-tech-topic/SKILL.md)에 해당 주장·버전·의문만 전달한다. 결과를 받아 관련 문장과 코드를 고친 뒤 해당 부분을 재확인한다. 문체 개선을 위해 조건이나 예외를 지우지 않는다.

코드는 가능하면 격리된 임시 환경에서 실행한다. 환경이 없다면 구문 확인과 공식 자료 대조 등 가능한 검증을 수행하고 실제 실행 여부를 작업 결과에 구분해 남긴다. 불필요한 전역 도구 설치나 저장소 의존성 변경은 하지 않는다.

## Writing Review

기술적 정확성 통과 여부와 별도로 글을 처음부터 읽는다.

- 사용자 직접 작성이 확인된 글의 문장 길이·말투·설명 깊이·소제목·코드 전후 설명과 크게 어긋나지 않는가. AI 작성 글이나 작성자 미확인 샘플을 사용자 문체로 단정하지 않는가.
- 보고서식 표현, 기계적인 “~합니다”·“~할 수 있습니다” 반복, 과도하게 동일한 문장 구조가 있는가.
- “~에서 확인할 수 있습니다”, “~를 참고할 수 있습니다”, “~에 따르면” 같은 출처 보고와 조사 과정이 본문을 차지하는가.
- 정의를 나열하기만 하는가. 독자가 궁금해할 이유와 사용 상황이 설명되는가.
- 같은 내용을 표현만 바꿔 반복하거나 절마다 요약하는가. 불필요한 서론·결론·친절한 해설이 있는가.
- 질문과 소제목이 실제 문맥을 연결하는가. 고정된 질문·답변 틀이나 예시 목차를 억지로 적용하지 않았는가.
- 출처 링크가 필요한 근거를 제공하면서 글의 흐름을 방해하지 않는가.

문제가 있으면 해당 문장·문단을 직접 다듬거나 불필요한 부분을 덜어낸다. 어미 치환만으로 해결하지 말고 논리와 연결을 살핀다. 유효한 설명과 작성자의 의도는 보존한다. 문체 기준이 불확실하면 사용자의 명시적 선호와 Writer의 기본 규칙을 적용한다.

## 저장소 형식과 렌더링 확인

세부 작성 규칙은 Writer의 “게시물 형식”을 기준으로 삼고 현재 `hugo.toml`, archetype, 관련 템플릿과 대조한다.

- 저장 위치·파일명·URL이 적절하고 기존 게시물과 충돌하지 않는지 확인한다.
- YAML Front Matter, 제목, 설명, 날짜·시간대, 초안 상태, category/tag의 키·자료형·기존 표기를 확인한다.
- 태그가 Writer의 분류 규칙에 따라 대표 분야를 첫 번째에 두고, 실제 다룬 기술·세부 주제로 이어지는지 확인한다.
- H1 중복, 소제목 계층, 닫히지 않은 코드 블록, 언어 표시, 표·목록 형식을 확인한다.
- 출처와 내부 링크의 대상, 이미지 파일 존재·배포 경로·대체 텍스트를 확인한다.
- 내용이나 렌더링에 영향을 주는 변경은 필요에 따라 `hugo server -D` 또는 초안 포함 빌드로 확인한다. 프로덕션 빌드는 `hugo --gc --minify`를 기준으로 검증하되, 초안이 제외된 빌드 성공만으로 해당 글의 렌더링을 검증했다고 하지 않는다.
- 기존 파일 보존이 요구되면 필요한 소스를 임시 디렉터리에 복사해 그 안에서 빌드한다. 출력·캐시·생성 리소스도 임시 위치를 사용한다. 지침 파일만 변경한 작업에는 사이트 빌드가 필요하지 않다.
- 현재 프로덕션 빌드는 초안과 미래 날짜 글을 제외한다. 미래 날짜만으로 예약 배포가 되지는 않는다. 검수를 이유로 `draft`를 임의로 해제하거나 배포하지 않는다.

## 완료 조건과 전달

1. 발견한 문제 중 요청 범위에서 해결할 수 있는 부분을 수정한다.
2. 수정이 영향을 준 기술 설명·코드·문체를 다시 확인한다. 불필요한 전체 재검수 루프는 만들지 않는다.
3. 검수된 Markdown을 요청된 최종 경로에 저장한다. 기존 글은 필요한 변경만 반영하고 새 글은 중복 파일을 만들지 않는다.
4. diff와 작업 전 상태를 비교해 대상 밖의 파일과 기존 사용자 작업이 보존됐는지 확인한다.
5. 최종 응답은 파일 경로, 주요 수정, 기술·문체 검수 결과와 실제 수행한 검증을 간결하게 전달한다. 해결하지 못한 사실이나 실행 제약은 별도로 명시하며 전부 검증됐다고 주장하지 않는다.
