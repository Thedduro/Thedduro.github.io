# 사전 관리

독자가 글에서 만난 개념을 짧게 찾아보고 관련 글로 이어갈 수 있게 한다. 사전 원본은 `data/glossary.yaml` 하나이며 화면은 `/glossary/`다. 용어별 Markdown이나 상세 페이지는 만들지 않는다. 글과 사전의 연결은 각 데이터 항목의 `related_posts` 한곳에서 관리하고, 게시글의 ‘이 글의 용어’는 템플릿이 역으로 찾아 표시한다.

## 글 작성·수정 흐름

1. 검수된 대상 글에서 이해에 필요한 핵심 개념을 추린다. 별도 정의가 도움이 되는 기술 개념·기술명·약어를 선택하고, 일반 단어·일회성 변수명·단순 언급은 제외한다. 정해진 개수를 채우지 않는다.
2. `data/glossary.yaml`의 `title`, `english`, `abbreviations`, `term_aliases`를 확인한다. 대소문자·공백·한영 표기·약어 차이를 고려해 같은 개념을 찾는다. 이름만 비슷한 다른 개념은 합치지 않고, 동음이의어는 분야를 제목에 명시한다.
3. 같은 개념이 있으면 해당 글을 `related_posts`에 중복 없이 추가한다. 글이 그 개념을 실제로 설명하거나 활용 방법을 보여주는지 확인한다. 기존 정의는 잘못됐거나 새 설명에 필요한 조건이 빠진 경우에만 수정한다.
4. 없으면 데이터 목록에 고유한 `id`를 가진 항목을 추가한다. 글과 무관하게도 이해되는 1~3문장 정의를 쓰고, 필요한 조건·기술 범위를 보존한다. 새로운 사실 확인은 [research-tech-topic](../research-tech-topic/SKILL.md)을 따른다. 기존 글의 충분한 근거는 재사용한다.
5. `related_terms`는 실제 존재하며 이해에 도움이 되는 항목만 연결한다. 신규 용어를 만들기 위해 연관 용어를 끝없이 추가하지 않는다. 글 수정으로 설명이 삭제됐다면 해당 글의 관련 링크도 다시 판단한다. 다른 글과의 연결은 임의로 삭제하지 않는다.
6. 기술적 정확성과 짧은 정의의 가독성을 각각 확인하고 아래 검증을 수행한다. 결과에 새로 등록한 용어와 기존 항목에 추가한 연결을 간결하게 보고한다. 후보가 없으면 억지로 등록하지 않는다.

새 글 작성·개념 설명 수정에는 이 사전 갱신이 포함된다. 오탈자·서식만 수정하거나 읽기 전용 검토를 요청받았다면 사전을 변경하지 않는다. 기존 게시물을 일괄 재검수하거나 커밋·push·배포하는 권한으로 해석하지 않는다.

## 저장 형식

`data/glossary.yaml`은 용어 객체의 YAML 배열이다. 새 항목 예시:

```yaml
- id: lazy-evaluation
  title: 지연 평가
  english: Lazy Evaluation
  abbreviations: []
  term_aliases: [지연 연산]
  description: 연산 결과가 필요할 때까지 실제 계산을 미루는 평가 방식이다.
  tags: [데이터 엔지니어링]
  related_terms: [spark-cache]
  related_posts: [/posts/spark-cache-when-to-use]
  sources: []
  draft: true
```

- `id`는 영문 소문자·숫자·하이픈으로 구성한 고유 식별자다. 사전 내부 주소 `/glossary/#term-<id>`에 쓰므로 연결 후 유지한다. `content/glossary/_index.md`는 목록의 제목·설명만 관리한다.
- `title`은 이 항목이 정의하는 **완전한 대표 이름**이다. 같은 계열에서는 이름의 수준을 맞춘다. 예를 들어 `데이터 레이크`, `데이터 레이크하우스`, `데이터 웨어하우스`, `데이터 마트`처럼 쓰고, `레이크하우스` 같은 줄임말은 `term_aliases`에 둔다. 정식 이름을 작은 별칭 줄에만 넣지 않는다. 제품명은 공식 표기를 유지한다.
- **일반 개념과 제품별 기능의 범위를 일치시킨다.** 일반 캐시의 정의와 Spark 캐시의 실행·저장 방식을 한 정의처럼 섞지 않는다. Spark 동작을 정의하는 항목은 제목을 `Spark 캐시`로 쓰고 정의 첫 문장에도 Spark와 대상(RDD·DataFrame 등)을 명시한다. 일반 개념에서 특정 제품을 예로 들 때는 예시임을 분명히 한다. 일반 개념도 필요하면 별도 ID로 등록하고 서로 연결한다.
- `english`는 같은 범위의 영문 명칭이다. `abbreviations`에는 실제 약어만, `term_aliases`에는 같은 개념의 한국어 별칭·음역 및 기타 영문 이름만 담는다. API 이름은 개념의 동의어가 아니므로 별칭 줄에 섞지 말고 필요한 경우 정의 안에서 대상 기술과 함께 설명한다.
- 표시 순서는 **대표 이름 → 영문 명칭 → 약어·별칭 한 줄**이다. 약어와 별칭은 `DW・웨어하우스`처럼 `・`로 연결하고 ‘약어’, ‘다른 이름’ 라벨은 붙이지 않는다. 데이터에서는 `abbreviations`와 `term_aliases`를 구분해 관리하되 화면에서는 약어를 먼저 표시한다. 각 배열 안의 원래 대소문자를 보존하며 소문자 사본을 검색용으로 중복 등록하지 않는다. `term_aliases`는 한국어 별칭·음역을 먼저, 기타 영문 이름을 다음에 둔다.
- 약어는 해당 개념을 지칭하는지 공식 문서·원전으로 확인한다. 예: 데이터 웨어하우스 `DW`, 데이터 마트 `DM`, 데이터 레이크 `DL`. `DL`을 데이터 레이크하우스에 재사용하는 식으로 서로 다른 개념의 약어를 옮기지 않는다. 영어 첫 글자를 조합해 임의로 만들거나, 항목마다 약어 칸을 채우기 위해 불확실한 약어를 추가하지 않는다. 근거가 기존 `sources`에 없으면 YAML 주석에 URL을 보존할 수 있다.
- `CORS`처럼 대표 이름 자체가 약어면 `english`에 정식 명칭을 두고 `abbreviations`는 `[]`로 두어 반복하지 않는다. 대표 이름이 영문 제품명이면 `english`는 비울 수 있다. 약어가 확인되지 않으면 빈 배열을 유지한다.
- 한국어·영문명·약어로 같은 항목을 찾을 수 있게 한다. 등록하지 않은 번역이나 동의어까지 자동 검색된다고 설명하지 않는다. 표기 검수는 배열 순서만 보지 말고 **화면에서 가장 크게 보이는 이름과 정의 첫 문장이 같은 개념을 가리키는지** 함께 확인한다.
- `description`은 1~3문장 정의다. 보충 설명만을 위한 별도 페이지는 만들지 않는다. 확인한 공식 출처는 `sources` 배열에 `{title: 출처 이름, url: https://...}` 형태로 보존한다.
- `tags`는 `데이터 엔지니어링`, `스토리지`, `클라우드`, `웹`처럼 큰 분야만 담는 문자열 배열이다. 실제로 여러 분야에 걸치면 복수 태그를 지정할 수 있다. `분석`·`성능` 같은 세부 개념이나 `Spark`·`Cloudflare` 같은 제품·기술명, `HTTP` 같은 프로토콜명은 태그로 추가하지 않는다. 예를 들어 Cloudflare 관련 용어는 `클라우드`로 분류한다. 기존의 큰 분야 표기를 우선 재사용하고, 새로운 분야가 필요할 때만 비슷한 수준의 카테고리를 추가한다. 이 예시는 고정 허용 목록이 아니며 사전 태그는 게시글 taxonomy와 별개다.
- `related_terms`는 같은 데이터 목록의 `id` 배열이다. 공개 항목은 사전 안의 위치로 연결된다. `related_posts`는 `content` 기준 절대 참조를 확장자 없이 적는다. 예: `/posts/data-platform-basics-1`. 파일명과 공개 slug가 다를 수 있으므로 공개 URL을 복사하지 않는다. 템플릿이 실제 제목과 주소를 구한다.
- `abbreviations`, `term_aliases`, `tags`, `related_terms`, `related_posts`, `sources`는 배열이다. 선택 항목이 없으면 `[]`를 쓴다. `draft`는 명시적인 boolean이며 신규 초안은 `true`로 둔다.
- `draft: true` 용어는 Hugo의 `--buildDrafts` 옵션과 관계없이 화면에서 제외한다. 새 용어는 해당 글과 같은 공개 의도로 작성하고, 검수 후 공개할 때만 `false`로 바꾼다. 기존 공개 용어에 초안·미래 게시글 참조를 저장해도 그 글의 링크는 공개 화면에서 제외된다.
- 독립적으로 유용한 정의는 관련 글이 없어도 유지할 수 있다. 사전 갱신 때문에 원본 글의 URL·날짜·태그를 바꾸지 않는다.

화면은 기본 가나다·ABC 순서로 배치하며 사용자용 정렬 선택 기능은 제공하지 않는다.

## 검증

- `hugo --gc --minify`로 빌드한다. 사전 템플릿은 필수 필드, 중복 ID·제목, 여러 태그의 형식, 용어 ID·게시글 참조의 존재를 검사한다. 중복 개념·부적절한 연결의 의미 판단은 직접 수행한다.
- `python3 scripts/check-seo.py public`으로 canonical·메타데이터·내부 링크를 검사한다. 검색 정책은 [optimize-search-seo](../optimize-search-seo/SKILL.md)를 참조한다.
- 초안 용어는 원본 데이터를 검수하고 렌더링이 필요하면 임시 복사본에서만 `draft: false`로 바꿔 확인한다. 원본 초안을 검증 목적으로 공개하지 않는다.
- 한글·영문·약어 검색, 복수 태그 표시·필터, 관련 글과 사전 내 앵커 연결을 확인한다. UI 코드를 바꾸지 않은 작업에서 전체 프론트엔드 테스트를 반복할 필요는 없다.
