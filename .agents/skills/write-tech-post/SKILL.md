# 기술 블로그 작성

개발자가 공부하고 이해한 내용을 자신의 언어로 정리한다. 공식 기술 문서나 보고서의 형식을 재현하는 것이 목적이 아니다.

## 작성 전: 실제 문체와 형식 파악

1. `hugo.toml`, `archetypes/default.md`, `content/posts/`와 필요한 `layouts/`를 읽어 현재 게시물 형식을 확인한다.
2. 사용자가 직접 작성한 것으로 확인되는 기존 글을 우선 읽는다. 사용자가 지정한 문체 샘플과 대화에서 확인된 작성 경위를 활용한다. Git 커밋 작성자나 파일이 오래됐다는 이유만으로 직접 작성했다고 단정하지 않는다.
3. 문장 길이, 말투, 설명 깊이, 소제목 방식, 코드 전후 설명, 개념 전개 방식을 짧게 파악한다. 기존 문장은 복사하지 않고 스타일만 참고한다.
4. 검증된 조사 결과를 읽고 부족한 사실이나 버전 차이는 [research-tech-topic](../research-tech-topic/SKILL.md)으로 확인한다. 충분한 조사를 다시 수행하거나 불확실한 내용을 자연스러운 문체로 덮지 않는다.

현재 샘플의 한계: `hello-world.md`는 소개용 초안으로 사용자 직접 작성 여부가 확인되지 않았고, `spark-cache.md`는 AI가 작성한 뒤 사용자가 문체 문제를 지적한 초안이다. 두 파일은 형식 참고용으로 사용할 수 있지만 사용자 고유 문체의 정답으로 삼지 않는다. 이후 사용자 작성·승인 샘플이 확보되면 그것을 우선한다.

확인된 사용자 작성 글이 없으면 그 한계를 작업 결과에 간단히 밝히고, 사용자가 명시한 문체 선호와 아래 규칙으로 진행한다. 샘플 요청만으로 작성을 멈추거나 문체 분석을 했다고 꾸미지 않는다.

## 글의 구성과 문체

- 한국어로 자연스럽게 작성한다. 기술명·API·명령어는 정확한 표기를 유지한다.
- 개념을 정의하는 데 그치지 않고 왜 필요한지, 어떤 상황에서 사용하는지, 어떤 대가나 제약이 있는지를 설명한다.
- 독자의 궁금증을 따라 내용을 연결한다. 예를 들어 문제 상황 → 왜 발생하는가 → 실제 동작 → 사용 시점 → 무조건 써도 되는가 → 코드 순서가 가능하다. 모든 글에 이 목차를 기계적으로 적용하지 않는다.
- 질문은 앞의 설명에서 실제로 생기는 의문일 때 사용한다. 질문형 소제목을 모든 절에 넣거나 매번 질문·답변 패턴을 반복하지 않는다.
- 모든 문장을 “~합니다”, “~할 수 있습니다”로 끝내지 않는다. 어미만 억지로 바꾸거나 반말과 존댓말을 무작위로 섞지 말고, 글의 말투와 문장 리듬을 자연스럽게 유지한다.
- 정의 → 정의 → 정의의 나열, 보고서식 구분, 모든 문단을 같은 길이와 구조로 맞추는 과도한 정돈을 피한다.
- 의미 없는 도입, 지나치게 친절한 설명, 당연한 전제의 장황한 해설, 같은 내용을 표현만 바꾼 반복을 덜어낸다.
- 절마다 요약을 붙이지 않는다. 결론은 독자가 판단하거나 실행할 내용이 있을 때만 넣고 본문을 재진술하지 않는다.
- 과장된 수식어와 “빠르게 변화하는 기술 환경에서”, “혁신적인”, “깊이 알아보겠습니다” 같은 상투어를 피한다.
- 사용자의 운영 경험, 장애 대응, 측정 수치를 지어내지 않는다. 예시 상황은 가상의 상황임을 알 수 있게 쓰되 매 문단에서 반복 고지하지 않는다.

## 조사 내용을 본문으로 옮기는 방법

- 검증된 사실을 이해한 뒤 작성자의 언어로 풀어낸다. 공식 문서의 문장이나 목차를 그대로 옮기지 않는다.
- “~에서 확인할 수 있습니다”, “~를 참고할 수 있습니다”, “~에 따르면” 같은 출처 보고형 표현을 반복하지 않는다. 무엇을 검색하고 확인했는지 조사 과정을 본문에 서술하지 않는다.
- 필요한 버전과 성립 조건은 해당 설명에 간결하게 포함한다. 사실, 해석, 권장 사항과 예상 결과·관측 결과를 구분한다.
- 근거가 필요한 경우 문장 끝에 짧고 의미 있는 출처 링크를 붙인다. 출처를 소개하는 별도 문장이나 불필요한 링크 나열로 흐름을 끊지 않는다.
- 확인하지 못한 핵심 주장은 다시 조사하거나 제외한다. 불확실성 때문에 설명의 의미가 달라진다면 그 조건을 명시한다.

## 게시물 형식

현재 설정과 원본이 바뀌었다면 다시 확인한 규칙을 우선한다. 아래는 이 저장소의 기본 작성 규칙이다.

### 파일과 Front Matter

- 새 글은 `content/posts/<영문-소문자-하이픈>.md`로 작성한다. 날짜 접두사는 필수가 아니다. `_index.md`는 목록 페이지이므로 게시물로 사용하지 않는다.
- 파일 맨 위에 `---`로 감싼 YAML을 사용한다. 아래 값은 예시이며 실제 글에 맞게 바꾼다.

```yaml
---
title: "글의 내용을 나타내는 제목"
date: 2026-09-21T09:00:00+09:00
draft: true
description: "글에서 다루는 문제와 핵심 내용을 담은 짧은 설명."
categories: ["Data Engineering"]
tags: ["Data Engineering", "Spark", "PySpark"]
slug: "example-topic"
---
```

- 기본 필드는 `title`, `date`, `draft`, `description`, `categories`, `tags`다. `slug`는 기본 archetype에 없는 선택 필드다.
- 날짜는 실제 작성·게시 의도에 맞게 한국 시간 `+09:00`을 포함한다. 예시 날짜를 복사하지 않는다. 새 초안은 불리언 `draft: true`로 시작하고 공개 요청에 맞춰 변경한다.
- `description`은 글 상단·목록 카드·메타 설명에 쓰이므로 글별로 작성한다. 카드에서는 최대 150자 길이로 축약된다.
- URL 설정은 `/posts/:slug/`다. `slug`가 없으면 제목을 기반으로 URL이 만들어진다. 새 글에는 파일명과 같은 영문 slug를 권장하며 파일명·URL 중복을 확인한다. 기존 글의 제목·slug·날짜·공개 상태는 요청에 필요하지 않으면 유지한다.

### 카테고리와 태그

- 키는 복수형 `categories`, `tags`이며 값은 문자열 배열이다. 비어 있으면 `[]`를 사용한다.
- 원본 게시물에서 현재 사용 중인 값을 먼저 확인한다. 현시점에는 카테고리 `Data Engineering`, 태그 `Data Engineering`, `Blog`, `Spark`, `PySpark`가 있다. 고정 허용 목록은 아니다.
- 기존 표기를 우선 재사용하고 대소문자·띄어쓰기·언어 표기를 불필요하게 혼용하지 않는다. 카테고리는 큰 주제로 고른다.
- 태그는 **대표 분야 → 구체적인 기술·세부 주제** 순서로 작성한다. 첫 태그는 글의 중심 분야 하나로 정하고, 뒤에는 본문에서 실제 다룬 기술과 주제를 둔다. 카테고리와 같은 분야를 첫 태그에 넣어도 된다.
- 분야 표기는 기존 `Data Engineering`에 맞춰 `Cloud`, `Frontend`, `Backend`처럼 일관된 영문을 사용한다. 이는 확장 가능한 예시이며 고정 허용 목록이 아니다. 여러 분야에 걸치면 글의 주된 관점에 맞는 분야를 맨 앞에 두고, 다른 분야는 실제 내용상 필요할 때만 추가한다.
- 예: Spark 글은 `["Data Engineering", "Spark", "PySpark"]`, 클라우드 인프라 글은 `["Cloud", "AWS", "Terraform"]`, 프론트엔드 글은 `["Frontend", "React"]`, 백엔드 글은 `["Backend", "Spring Boot"]`. YAML 배열 순서를 유지한다.
- 적절한 기존 값이 없으면 새 값을 추가할 수 있다. 관련 없는 태그나 기존 글의 분류 일괄 변경은 하지 않는다. 개수 제한은 없지만 목록 카드에는 태그가 최대 4개 표시된다.

### 본문, 코드, 이미지

- 제목은 템플릿에서 H1으로 출력한다. 본문에 `# 제목`을 중복하지 않고 `##`, `###`로 전개한다. 문단·목록·코드 블록 사이에 빈 줄을 둔다.
- 목차·읽기 시간·코드 줄 번호는 자동 생성에 맡긴다. 현재 raw HTML은 제한되고 Mermaid·수식 렌더러·사용자 정의 shortcode는 구성되어 있지 않다.
- 코드가 이해에 도움이 될 때만 간결한 예제를 넣고 fenced code block에 언어를 지정한다. 입력, 필요한 import·의존성·버전과 핵심 동작을 이해할 만큼 설명한다.
- 실행 가능한 예제와 의사 코드·발췌를 구분한다. 측정하지 않은 수치를 쓰거나 실행하지 않은 예제를 검증했다고 표현하지 않는다. 실제 키·토큰·개인정보는 넣지 않는다.
- 아직 게시물 이미지의 기존 사용 사례는 없다. 기본 저장 위치는 `static/images/<slug 또는 파일명>/`로 하고 본문에서는 `![설명](/images/<글 식별자>/파일명.png)`으로 참조한다.
- 이미지 URL에는 `static`이나 로컬 절대 경로를 넣지 않는다. 실제 파일 존재와 대체 텍스트를 확인하고 필요한 출처를 붙인다. `assets/`에 넣기만 하면 배포된다고 가정하지 않는다.
- 기존 게시물로 연결할 때는 파일명만으로 URL을 추정하지 않고 Front Matter와 permalink 설정을 확인한다.

## 검수로 전달

대상 경로, 초안, 조사 근거와 기준 버전, 문체 참고 자료의 출처·한계, 예제 실행 여부와 남은 쟁점을 [review-tech-post](../review-tech-post/SKILL.md)에 전달한다. 별도 보고서 파일은 요청이 없으면 만들지 않는다.

초안은 메모리나 임시 위치에서 작성할 수 있다. 게시물 경로에 먼저 저장한 경우에도 검수 전에는 완료로 보고하지 않는다. 검수를 거친 Markdown을 최종 경로에 저장하고 작성 파일과 검증 범위를 간결하게 전달한다.
