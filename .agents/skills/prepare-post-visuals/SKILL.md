# 게시물 시각 자료 준비

Visual은 설명의 일부다. 이미지 개수나 장식성을 늘리는 것이 아니라, 텍스트만으로 전달하기 어려운 흐름과 관계를 이해하기 쉽게 만드는 것이 목적이다. 자료를 추가하지 않는 판단도 정상적인 완료 결과다.

## 먼저 게시물과 환경 확인

- 대상 게시물 전체와 요청 범위를 읽는다. 관련 조사 결과, 기준 버전, 코드와 본문에서 사용하는 용어를 확인한다.
- 기존 게시물의 이미지 참조, `static/`, `assets/`, `hugo.toml`, 관련 `layouts/`를 확인한다. 저장·참조 규칙은 현재 구조와 [write-tech-post](../write-tech-post/SKILL.md)의 게시물 형식을 따른다.
- Mermaid는 실제 렌더링 설정이나 동작하는 기존 예제로 지원 여부를 확인한다. Hugo를 사용한다는 사실이나 코드 블록 문법만으로 지원한다고 판단하지 않는다.
- 이 Skill을 추가하는 시점에는 게시물 이미지 사례가 없고 `static/favicon.svg`만 존재하며, Mermaid 렌더러는 구성되어 있지 않다. 이후 환경이 바뀌었으면 실제 확인 결과를 우선한다.

## 필요성과 유형 판단

다음 중 독자의 이해가 실제로 나아지는 지점을 찾는다.

- 여러 단계의 흐름을 문장만으로 따라가기 어려운가?
- 데이터 이동, 실행 순서, 시스템 구조나 컴포넌트 관계를 함께 볼 필요가 있는가?
- Before / After를 나란히 비교하면 차이가 더 명확해지는가?
- 공식 UI나 원본 Architecture Diagram 자체를 보여줘야 설명이 성립하는가?

각 후보에 대해 전달할 핵심과 배치할 절을 정한다. 본문을 그대로 상자로 옮긴 그림, 같은 설명을 반복하는 그림, 주제와 분위기만 맞는 장식 이미지는 추가하지 않는다. 그림을 빼도 이해에 차이가 없다면 텍스트를 유지한다.

| 유형 | 선택 기준 |
| --- | --- |
| 직접 작성하는 Diagram | 데이터·실행 흐름, 처리 과정, 시스템 구조, 개념·컴포넌트 관계, Before / After를 설명할 때 우선 고려 |
| 외부 이미지 | 공식 Architecture Diagram, UI Screenshot, 기술 Diagram 등 원본 이미지 자체를 보여주는 데 의미가 있을 때 사용 |

기술 개념을 설명할 때는 일반적인 이미지 검색보다 직접 Diagram으로 표현할 수 있는지 먼저 판단한다. 적합한 자료를 찾지 못했다고 장식 이미지로 대신하지 않는다.

## 기술적 근거와 Research 연계

- Diagram의 노드·화살표·순서·조건도 기술적 주장이다. 본문과 [research-tech-topic](../research-tech-topic/SKILL.md)의 검증 결과에 맞춘다.
- 조사 결과가 부족하면 해당 Skill로 필요한 사실만 확인한 뒤 돌아온다. 예를 들어 Spark cache 내부 동작을 표현할 때 저장 위치, 실행 시점, 재사용 경로를 추측해 그리지 않는다.
- 버전별 차이, 조건부 동작, 예외 경로를 무조건적인 흐름처럼 표현하지 않는다. 단순화가 의미를 바꾼다면 필요한 조건이나 범위를 짧게 표시한다.
- 공식 이미지와 본문의 대상 버전·제품·API가 맞는지도 확인한다. 시각 자료에 맞추려고 본문의 사실을 바꾸지 않는다.

## 직접 작성하는 Diagram

- 한 그림이 설명할 핵심을 정하고 그에 필요한 관계와 흐름만 남긴다. 불필요한 노드, 아이콘, 색상과 교차 화살표를 줄인다.
- 본문과 같은 용어를 사용하고 화살표가 데이터 이동인지 실행 순서인지 관계인지 분명하게 한다. Before / After는 같은 요소와 비교 기준을 유지한다.
- Mermaid가 지원된다면 간단한 기술 Diagram에 우선 고려한다. 지원하지 않으면 렌더링되지 않는 `mermaid` 코드 블록을 게시물에 넣지 않는다.
- Mermaid 미지원 환경에서는 사용 가능한 도구로 정적인 SVG 또는 PNG Diagram을 작성해 일반 Markdown 이미지로 삽입한다. 정확한 라벨과 관계를 제어할 수 있는 방법을 선택한다. 필요하면 임시 작업 공간에서 생성·렌더링한다.
- 시각 자료 작업을 이유로 테마·JavaScript·Hugo 설정을 임의로 바꾸지 않는다. 사용 가능한 방법으로 표현하기 어렵다면 본문을 유지하고 제약을 작업 결과에 밝힌다.
- 직접 작성한 그림은 공식 도식이나 실제 실행 캡처인 것처럼 표시하지 않는다. 외부 이미지의 구성이나 그림을 그대로 베껴 직접 작성한 자료로 취급하지 않는다.
- 글자가 본문 폭과 모바일 화면에서도 읽히는지, 화살표와 라벨이 겹치지 않는지, 밝고 어두운 배경에서 구분되는지 확인한다. 색상만으로 의미를 구분하지 않는다.

## 외부 이미지 조사와 재사용

공식 Documentation → 공식 GitHub → 공식 기술 블로그 → 라이선스가 명확한 외부 자료 순으로 조사한다. 이미지 검색 결과는 원본을 찾는 단서로만 사용한다.

포함하기 전에 다음을 실제 원본 페이지에서 확인한다.

- 이미지 원본 URL과 이를 설명하는 출처 페이지, 작성·제공 주체.
- 대상 이미지에 적용되는 라이선스나 재사용 허용 근거. 공식 출처라는 이유만으로 재사용 가능하다고 간주하지 않는다.
- 출처·저작자·라이선스 표시, 변경 고지 등 필요한 조건. 저장소 코드의 라이선스가 제3자 이미지에도 적용되는지 따로 확인한다.

재사용 가능 여부가 불분명하면 다운로드·복사·외부 URL 임베드로 게시물에 포함하지 않는다. 필요한 경우 원본 페이지로 연결하거나, 검증된 기술 내용을 독립적인 Diagram으로 설명한다. 외부 이미지 자체가 꼭 필요하지 않다면 직접 Diagram을 우선한다.

허용이 확인된 자료만 필요한 파일로 저장하고 조건에 맞는 출처 표시를 붙인다. 크롭·라벨 변경 등이 허용되는지도 확인하며 의미를 왜곡하지 않는다. 원본 URL, 출처, 재사용 근거와 적용 조건은 검수에 전달한다. 요청이 없으면 별도 조사 보고서 파일을 만들지 않는다.

## 배치와 파일 관리

- 그림이 설명하는 개념이 등장하는 위치 가까이에 배치한다. 필요한 곳에만 넣고 문단의 논리를 끊지 않는다.
- 그림 전후에는 문제·동작·차이를 직접 설명한다. “아래 이미지에서 확인할 수 있습니다”, “다음 그림을 참고하세요”, “위 그림에서 볼 수 있듯이” 같은 보고서식 유도 문장을 반복하지 않는다.
- 대체 텍스트는 그림의 핵심 의미를 설명한다. 캡션은 그림의 범위나 출처 등 필요한 정보만 담고 본문을 반복하지 않는다.
- 현재 기본 저장 위치는 `static/images/<slug 또는 파일명>/`이고 본문 참조는 `/images/<글 식별자>/<파일명>`이다. 기존 규칙이나 실제 구조가 변경됐다면 먼저 확인한 규칙을 따른다.
- 파일명은 `spark-cache-flow.png`, `spark-without-cache.png`, `kafka-consumer-flow.svg`처럼 내용을 나타내는 영문 소문자와 하이픈을 사용한다. 확장자는 실제 형식과 일치시킨다.
- URL에 `/static`이나 로컬 절대 경로를 넣지 않는다. `assets/`의 파일은 배포 처리 없이 바로 참조할 수 있다고 가정하지 않는다. `public/` 생성물을 직접 수정하지 않는다.
- 기존 이미지나 다른 글에서 공유하는 파일을 덮어쓰지 않는다. 새 자산과 대상 글의 필요한 연결 문장만 변경한다. 원본 수정이 금지된 작업에서는 배치 제안과 준비한 자료만 전달한다.
- 재편집에 필요한 Diagram 원본을 보존할 때는 기존 자산 관례를 따르고, 출력과 원본이 각각 무엇인지 명확하게 한다. 생성 스크립트·중간 파일·새 의존성을 불필요하게 저장소에 남기지 않는다.

## 검수와 완료

- 새 시각 자료와 주변 문장이 본문·코드·조사 결과에 일치하는지 확인한다. 외부 이미지는 출처와 재사용 조건을 다시 확인한다.
- 삽입한 그림은 실제로 렌더링해 내용·가독성을 살핀다. 파일 존재와 Markdown 경로도 확인한다. Mermaid를 사용했다면 게시물에서 실제 Diagram으로 표시되는지 확인한다.
- 사이트 검증은 [review-tech-post](../review-tech-post/SKILL.md)의 렌더링 확인 절차와 연결하고, 검증된 자료·배치 위치·변경 파일·남은 제약을 전달한다. 검수 중 호출됐다면 변경 부분 검수로 돌아가며 새 글 작성 흐름을 다시 시작하지 않는다.
- 최종 결과에서는 추가한 자료와 역할을 간결하게 설명한다. 불필요하다고 판단했다면 자료를 추가하지 않았다는 판단만 전달한다. 시각 검증을 수행하지 못했으면 완료한 것처럼 표현하지 않는다.
