# 기술 주제 조사

Writer가 이해하고 자신의 언어로 설명할 수 있도록 사실과 근거를 제공한다. Research 결과는 블로그 본문이 아니다.

## 조사 범위 결정

- 요청에서 기술, 사용 환경, 독자가 궁금해할 핵심 동작을 파악한다. 기존 글 검수에서 호출했다면 지적된 주장과 코드 범위에 집중한다.
- 사용자가 지정한 버전이 있으면 그 버전을 기준으로 삼는다. 없으면 저장소·예제의 환경을 확인하고, 여전히 불명확하면 적합한 기준 버전을 정해 결과에 명시한다. 확인 없이 최신 버전이라고 부르지 않는다.
- 기존 조사 결과가 있으면 근거·버전·대상 API가 현재 요청에 맞는지 확인한다. 충분한 근거는 재사용하고 부족하거나 변경 가능성이 있는 부분만 추가 조사한다.

## 사실과 근거 확인

1. 공식 Documentation에서 API 계약, 기본값, 실행 시점, 저장·처리 방식, 제약을 확인한다. 이름이 비슷한 API나 언어별 구현을 구분한다.
2. 문서만으로 해소되지 않는 동작은 프로젝트·유지관리 조직의 공식 GitHub에서 소스와 테스트를 확인한다. 기준 버전의 태그 또는 커밋을 사용하고 변경 중인 기본 브랜치와 혼동하지 않는다.
3. 버전별 기본값·API·동작 차이가 쟁점이면 Release Note와 마이그레이션 문서를 확인한다. 이슈나 PR의 제안을 출시된 기능으로 취급하지 않는다.
4. 핵심 주장마다 실제로 열어 확인한 근거를 연결한다. 공식 문서와 소스가 다르면 적용 버전·조건을 다시 살펴보고 불일치를 남긴다.
5. 코드가 핵심 근거라면 가능한 범위에서 최소 예제를 실행한다. 실행 환경이 없으면 문서·소스 검증과 구문 검사를 구분하고, 실행하지 않은 결과를 관측값으로 쓰지 않는다.

공식 문서와 공식 GitHub를 우선한다. 제3자 글은 탐색의 단서나 보조 자료로 사용할 수 있지만 핵심 동작은 가능한 한 공식 자료로 교차 확인한다. 저장소가 공식인지 소유자와 프로젝트의 연결을 확인한다.

## Writer에게 전달할 결과

주제에 필요한 만큼 간결하게 정리한다. 모든 조사에 같은 분량이나 표를 강제하지 않는다.

- **대상과 버전:** 기술, API, 실행 환경, 적용 범위.
- **핵심 사실과 근거:** 주장별 사실, 성립 조건·예외, 문서 절 또는 소스 URL. 필요하면 버전·태그·커밋을 함께 남긴다.
- **설명에 필요한 맥락:** 해결하려는 문제, 사용하는 이유, 실제 사용 상황, 비용과 한계. 사실에서 도출한 해석이나 권장 사항은 구분한다.
- **예제 재료:** 최소 입력, 코드에 필요한 API, 예상 결과와 실제 실행 여부.
- **미확인 사항:** 확인되지 않은 주장, 자료의 불일치, 추가 확인이 필요한 지점. 없는 수치나 출처를 채워 넣지 않는다.

## Research와 Writing의 경계

- “공식 문서에 따르면”, “공식 문서에서 확인할 수 있습니다”, “자세한 내용은 ~에서 확인할 수 있습니다” 같은 표현을 본문용 문장으로 전달하지 않는다. 사실과 링크를 구분해 넘긴다.
- 출처의 문장을 번역·재배열한 글이나 조사 일지를 완성된 게시물로 내놓지 않는다. 필요한 짧은 인용은 인용임을 명시하고 근거와 연결한다.
- 단순 조사 요청에서는 조사 결과만 전달한다. 별도 요청 없이 게시물·설정·리서치 보고서 파일을 만들거나 변경하지 않는다.
- 작성 흐름에서는 결과를 [write-tech-post](../write-tech-post/SKILL.md)에 전달한다. 검수 중 호출됐다면 해당 결과만 [review-tech-post](../review-tech-post/SKILL.md)에 돌려주며 작성 흐름을 새로 시작하지 않는다.
